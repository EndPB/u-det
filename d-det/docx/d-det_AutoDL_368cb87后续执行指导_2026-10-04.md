## 3. 首轮基线复现

首轮方法是 source 隔离的字符级 TF-IDF cosine：`char_wb`、2–5 gram、`min_df=2`、最多 60,000 特征。阈值只在 dev 选择；test 只读取一次；bootstrap 按 `task_id` 聚类。

```bash
mkdir -p artifacts/h2_pair_round1
python scripts/audit_h2_pair_benchmark_v1.py
python scripts/h2_pair_similarity_baseline.py \
  > artifacts/h2_pair_round1/similarity_baseline.stdout.json
```

若审计脚本因缺少三个 source package 报路径错误，不要解压其它包；改为读取：

```text
data/h2_pair_benchmark_v1/audit_index.json
```

并回传错误、`rows`、`invalid_records` 和 checks。脚本原始布局可能需要项目根下的最小兼容链接：


## 4. 必须保存的结果

主结果：

```text
artifacts/h2_pair_round1/similarity_baseline.json
artifacts/h2_pair_round1/similarity_baseline.stdout.json
```

每个 source/view 都要保留：

- dev/test balanced accuracy、F1、ROC-AUC、average precision；
- 正例和负例平均 cosine；
- `family_pair_balanced_test`；
- task-cluster bootstrap 结果。

两个 source 必须分开报告：`authorbench_dcan` 与 `llm_codegen_v2`。五个 view 必须分开报告：`raw`、`ids_only`、`strings_only`、`comments_only`、`all`。

## 5. 结果解释规则

1. `raw` 或 `all` 变好，只能说明表面代码相似度有可读信号，不能写成家族语义已经被学到。
2. `ids_only`、`strings_only`、`comments_only` 的变化用于定位标识符、字符串和注释捷径。
3. `family_pair_balanced_test` 是严格诊断子集，不替代普通 test；LLM-CodeGen 的 family-pair 数量较小。
4. test 结果不能用于挑选 view、阈值、seed 或损失。
5. 任何 source 或 split 单独改善，都只能作为诊断，不扩展为统一结论。

## 6. 下一轮编码器实验门槛

当前 TF-IDF 基线显示：表面信号确实存在，但两个 source 的最佳 view 不一致。因此可以做一个小规模、受控的编码器/对比学习实验，但先固定 TF-IDF 作为对照。

建议顺序：

1. 冻结现有表示，只训练线性 family head；
2. 在相同 task-clustered split 上加入轻量 SupCon 或距离约束；
3. 只使用同任务、同 source、同 split、同家族、不同 generator 的正对；
4. 以 `raw`、`ids_only`、`strings_only`、`comments_only`、`all` 的同协议结果判断是否超越 lexical shortcut；
5. 只有两个 source 同时改善，且清洗视图仍保持增益，才进入更大预算。

不得把不同任务的相似代码构成正对；不得把 STACAD 跨厂商 generator 当作同家族正对；STACAD 只作为外部控制和泛化检查。
