# 同门代码仓库数据集：元数据摘要与 ACL 适用性计划

日期：2026-10-01  
范围：只做文件系统元数据审计与研究设计；不读取 JSONL 内容，不下载，不生成样本，不训练。

## 1. 当前本地可核实摘要

数据根目录为 `datasets/`。目录下共有 154 个 JSONL 文件，文件总大小约 35.70 GiB（PowerShell `Length` 求和；未加载文件内容）。文件按五类组织：

| 类别 | 文件数 | 大小 |
|---|---:|---:|
| `commit` | 23 | 0.735 GiB |
| `diff` | 23 | 7.766 GiB |
| `file` | 23 | 24.098 GiB |
| `function` | 62 | 1.097 GiB |
| `pr` | 23 | 2.003 GiB |
| 合计 | 154 | 35.70 GiB |

23 个仓库级来源同时出现在五类数据中，包括 `microsoft_vscode`、`mlflow_mlflow`、`oven-sh_bun`、`calcom_cal.com`、`dotnet_aspire`、`airbytehq_airbyte` 等。`function` 文件名显示至少覆盖 C、C#、C++、Go、Java、JavaScript、Python、TypeScript 八种语言；语言文件数量和字节数高度不均衡，TypeScript 与 Python 占比较大。

这些信息支持一个保守描述：这是一个以真实开源仓库为来源、按软件工件粒度组织的多语言代码语料，包含仓库提交、补丁、文件、函数和 PR 级视图。它不是“已证实的 AI 代码检测数据集”：当前目录名、文件名和大小没有提供 Human/AI 标签、生成器、模型家族、prompt、采样参数或人机配对证据。

## 2. 与当前 d-det 主线的关系

当前主线已经把问题收窄为：后训练差异动机 → 768 维表示中的闭集来源可读性 → 跨 generator 迁移损失与数据构型分析。E35 的云端会话记录显示，跨 generator 方法增量约为 0.28–0.30 个百分点，未达到预先设定的实用门槛；因此下一步是最终审计和论文写作，不能把新数据集直接当作“继续调损失”的理由。

这个本地数据集的价值主要在于真实仓库结构、跨文件粒度和跨语言环境，可用于：

1. 真实软件工件上的分布与切分诊断；
2. 研究同一仓库内 commit/diff/file/function/PR 的近重复和泄漏；
3. 在取得可靠来源标签后，构造 repository-held-out 或时间切分的外部稳健性评测。

它目前不适合作为当前 H2 的直接主训练集，原因是 H2 需要同一家族、不同 generator 的可识别标签和不相交 generator 切分；本地目录尚未显示这些字段。若只有仓库名，模型很可能学习项目、语言、风格或重复代码，而不是 generator/family 关系。

## 3. 必须先确认的字段与风险

在服务器上只读取 JSONL 的少量首行或 schema（流式、单行、不会把数据集载入内存）之前，需要从同门提供的数据说明或 schema 中确认：

- 每条记录的唯一 ID、仓库、commit/PR、文件路径、函数范围和时间戳；
- `label` 的定义：Human、AI、Hybrid、未知，及其标注来源；
- generator、model family、具体模型版本、role（base/instruct/reasoning）和生成时间；
- prompt、上下文、patch 操作或重写方式，是否存在人机配对；
- 语言、仓库许可证、去重规则、过滤规则和失败样本处理；
- 官方 train/validation/test 切分及其是否按仓库、时间、任务或生成器隔离。

特别要防止五类工件之间的泄漏：同一文件会同时出现在 file、function、commit、diff、PR；同一修改链会产生高度相似的样本。任何随机行级切分都不能作为主评测。主切分应优先按 repository 或事件链分组，必要时再按时间冻结。

## 4. 分阶段、低资源审计计划

### 阶段 A：本地元数据（已完成）

仅统计路径、扩展名、字节数、类别、仓库数和语言文件名。已避免解码 JSON、统计行数、去重、tokenize、embedding 和 GPU 操作。

### 阶段 B：服务器 footer/流式 schema（待授权后执行）

先只读取每类文件的首条记录或 JSON schema，输出字段名、类型、缺失率的抽样报告；每次只处理一个文件、固定小缓冲区。若没有 schema，先对每个类别抽取不超过 3 条记录，仅用于确认字段，不保存代码正文。

### 阶段 C：可行性分流

根据字段结果将数据分为：

- **主线候选**：有可靠 Human/AI 与 generator/family，且能按仓库或事件链切分；
- **外部诊断集**：只有真实仓库结构或人机标签，缺 generator/family；
- **不适合主线**：标签含义不清、切分泄漏严重、或只有同一来源项目。

### 阶段 D：最小实验设计（仅在满足主线候选条件时）

先用每类 2–4 个仓库、每语言少量样本建立 CPU/4GB 显存可运行的审计子集；冻结现有编码器和 B0 主轴，只做离线表示探针、长度/语言/仓库分桶、重复率和 generator-held-out 评测。不要先训练新模型，也不要把 35GB 全量复制到本机。

## 5. 与 Hugging Face 资源的关系

公开资源可以用于**方案对照和字段设计**，不应在本机下载：

- CoDET-M4 的公开卡片显示其包含 code、language、model、split、target、source 等字段，适合检测与多 generator 归因的字段参考；
- SemEval 数据卡片显示 `generator`、`model_family`、`generation_mode`、`source`、`language`、`label` 等字段，适合作为当前 H2 所需 schema 的参照；
- HybridCodeAuthorship 是行/块级人机混合代码基准，适合细粒度检测对照，但不是跨 generator 家族归因数据。

这些公开页面只用于检索和设计参考；本轮没有下载或生成任何数据。

## 6. 预先结论与补充建议

当前数据集**适合做真实仓库分布与外部稳健性研究，暂不够做 H2 主实验**。最小必要补充不是更多代码，而是标签和切分元数据：

1. generator/model family/role 的逐样本标签及其来源；
2. 人类、模型生成、编辑或混合的标注协议；
3. prompt/任务或变更事件 ID，以便构造同题配对和事件级去重；
4. repository、时间、commit/PR 图和官方 split；
5. 一份不含代码正文的 schema、字段字典和许可说明。

若这些信息无法提供，应把该数据集定位为“真实仓库外部诊断集”，用于检测性能、跨仓库迁移、长度/语言/工件粒度分层和泄漏审计；论文中不得把它解释为 generator-family 因果证据。

## 7. 当前禁止事项

在用户明确改变约束前：不下载 Hugging Face 数据，不处理本地 35GB 内容，不生成新样本，不运行训练，不在 3050 4GB/16GB 机器上做全量 tokenize 或 embedding。

## 8. 公开数据集筛选结论（补充）

针对当前 H2，理想数据的最小结构不是“更多代码”，而是：

```text
code, human_ai_state, generator_id, model_family, role,
task_or_source_id, language, domain, decoding_or_edit_metadata,
repository_or_source, split
```

其中必须满足：

1. 至少 5 个 family；每个主要 family 至少 2 个 generator，最好 3 个以上；
2. 同一任务/来源尽量有多个 generator 的样本，避免把任务内容当成 generator 信号；
3. train/validation/test 按 generator 做 family-conditional held-out 切分；
4. Human 作为检测对照，不伪装成某个 generator；
5. 能区分 fully machine、human、machine-refined/hybrid 和 adversarial；
6. 记录语言、领域、模型 role、规模和采样参数，便于做角色/规模分层；
7. 能按源样本、任务或仓库做近重复审计，禁止随机行级切分掩盖泄漏。

按这个标准，优先级如下：

| 优先级 | 数据集 | 用法 | 判断 |
|---|---|---|---|
| 1 | `project-droid/DroidCollection` | H2 主候选；从已有 `generator`/`model_family` 标签重做两折 generator-held-out | 字段最完整，覆盖多语言、多领域、Human/AI/Refined/Adversarial；先做 schema 与计数审计 |
| 2 | `DaniilOr/SemEval-2026-Task13` | 外部迁移与复核；使用 Task B 的 family/未见作者设置，Task A/C 做检测和混合诊断 | 官方任务已经明确未见 generator family、语言和领域设置；不把官方随机/竞赛 split 直接当 H2 证据 |
| 3 | `CoDET-M4` / `CodeMirage` | 检测基线、语言/领域 OOD、重写鲁棒性 | generator/family 数量或配对信息不足以单独支撑 H2 |
| 4 | `HybridCodeAuthorship` | 行/块级 hybrid 检测附加实验 | 适合细粒度检测，不适合跨 family 归因 |
| 5 | `LLM-AuthorBench`、`LLM-NodeJS` | 受控 attribution sanity check | prompt 和 generator 清楚，但主要是全 AI 生成，缺可靠 Human 对照与跨 family 迁移协议 |

因此，最合理的开源路线是：**DroidCollection 做主候选，SemEval 做外部验证，HybridCodeAuthorship 做 hybrid 附加验证；本地 35GB 数据暂作真实仓库外部诊断集。** 只有在 DroidCollection 的字段审计确认每个 family 内有足够的多个 generator、且能构造不相交 generator split 后，才值得继续 H2；否则直接收窄为检测与闭集/描述性归因。
