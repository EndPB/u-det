## A. 方法论（最贵的一类）

### A1 ★★★ 2 epoch 的读数在本项目已经**六次**指向错误结论

单次训练的前几个 epoch 存在一种"**热身更快**"的假象：新改动看起来全面领先，
但到周期末端优势就缩水甚至反向。四次实例：

| # | 2 epoch 时的结论 | 对齐预算后 |
| --- | --- | --- |
| ① | "LoRA 微调对样本级有害"（0.8999 vs 冻结 0.9047） | 4ep 后 LoRA **0.9307 全面碾压** 冻结 0.9086 |
| ② | "门控是干净的正收益"（m4 +2.24 @2ep） | 4ep 只剩 **+0.17**、6ep **+0.73**，且方向随预算变化 |
| ③ | v0.4.1 的 e0 领先 v0.4.0 **+16.45**（line） | 周期末端只剩 **+0.79** |
| ④ | v0.4.4 的 line/token 比 v0.4.2 **+0.36 / +0.60** | 4ep 退回 **−0.17 / −0.03**（噪声级） |
| ⑤ | v0.4.5 的 line/token 比 v0.4.4 **+0.72 / +0.56**（"设计意图命中"） | 4ep **放大到 +1.02 / +0.94** —— 罕见：**2ep 是低估而非高估** |
| ⑥ | v0.4.5 在 `[512,2048)` 桶的 chunk 比 v0.4.4 **−2.62**（看着像"bypass 伤害中桶"） | 4ep 恢复为 **+0.25 并反超基线** ⇒ 差点据此写出错误的"按长度门控"方案 |

★ ⑤⑥ 与其他四例**方向相反**：那四例是"2ep 高估"，这两例是"2ep 低估"。
所以结论不是"小预算的数字要大打折扣"，而是**它只能定方向、不能定幅度**。

**规则**
1. 任何"A 比 B 好"的**架构/损失**结论，必须在**对齐 epoch 预算**后才成立；
2. **2 epoch 只能用来排优先级**，不能用来下结论；
3. 看趋势时**只看周期末端**（见 A2），中间轮的涨跌不算数。

*证据：`docx/u-det-v0.4.md` §7.3 / §7.4.2 / §8.9.2。*

### A2 ★★★ 判断"到顶"要看周期末端是否创新高，**不看损失**

本项目用 OneCycle-on-resume，每次续跑都相当于一次热重启，行为是 SGDR：
**先砸一个坑，再收回并创新高**。所以：

* 判据是 `mean = (val m4 F1 + val line F1) / 2` 的**周期末端值是否还创新高**；
* ❌ 不能看 train loss：v0.3.1 到顶那一轮 loss 0.676 是**全程最低**，只看损失会误判成"远未收敛"；
* ❌ 不能看中间的轮次：热重启的第一轮必然掉。

*证据：`docx/u-det-v0.4.md` §7.3.1 / §7.4.1（v0.4.0 到 6 epoch 仍在创新高）。*

### A3 ★★ 必须先让基线到顶，再比新架构

否则比的是"新架构 + 少训 vs 旧架构 + 多训"，而这个偏差足以让结论完全反过来（见 A1 的 ①）。

### A4 ★★ 平均分会把相反趋势抵消 —— 一定要分桶

在**长度分桶**上，U-Det 与基线的强弱方向是相反的：

* `[0,512)` 短文档：基线大幅领先（line −5.22 / chunk −6.23）
* `>8192` 长文档：U-Det 大幅领先（line +5.55 / chunk +7.84）

只看全测试集的平均分，这两个趋势**互相抵消**，结果看起来"差不多"，
于是既掩盖了真正该修的短文档瓶颈，也埋没了长文档上的结构优势。

★ 这条推广开来：**任何"平均分"都要先问一句"它是不是在掩盖反向的子群差异"**。

*证据：`docx/u-det-v0.4.md` §8.10.2。*

### A5 ★★ 项目里出现"这是固有代价 / 只能这样"的说法时，去质疑**实现**

本项目吃过一次大亏：`seq_len=1`（逐 token 编码 ⇒ attention 退化 ⇒ **q/k 是死参数**）
从 v0.2 就被发现并记录，但当时的结论是"**这就是逐 token 语义的固有代价**，
LoRA 目标只能取 `[v, o, wi, wo]`" —— **没人去问"为什么必须逐 token"**。

而它根本不是语义要求，只是实现方式的产物。等 v0.4.2 把它改成分块（块内 K=128 个 token
真实互相关注），**四项指标一次性 +2.92 / +7.56 / +10.65 / +7.01** ——
比之前两次结构改造（门控 +1.52、损失 +1.33）**大一个数量级**。

**规则**：把这类说法当成"待办疑点"，而不是约束。它往往就是最大的那个改进点。

*证据：`docx/u-det-v0.4.md` §8.7.8 / §9.1.2。*

### A6 ★★ "少算 ≠ 快"：延迟受限的系统里要减少**固定开销**，不是减少工作量

v0.4.2 首次跑时踩到：分块编码器**总算量降到 0.44 倍**，结果**慢了 1.62 倍**
（0.396 s/步 vs v0.4.1 的 0.244）。原因是 `compile=false` + GEMM 变小，
而每次前向的固定开销没变 ⇒ 每 token 反而更贵。

改成 `static + compile`（把块数补齐到固定形状、拿到单一静态图）后：
**0.396 → 0.24 s/步、GPU 利用率 29% → 78%、功耗 134W → 235W**。

**规则**：本项目长期是 **batch=1 的延迟受限**状态（GPU 利用率只有 ~30%）。
优化时先问"瓶颈是算力还是固定开销"，答案几乎总是后者。

*证据：`docx/u-det-v0.4.md` §8.7.6。*

### A7 ★ 单变量原则 —— 但**要显式声明**它是什么，并记下被推迟的变量

v0.4.2 为了保持"逐位置 → 分块"这一个变量，**故意**没有把 q/k 加进 LoRA 目标
（分块让 q/k 从死参数复活，本该顺手加）。这个决定是对的，但**必须写下来**，
否则它会永久躺在"忘了试"的列表里。

**规则**：每次实验的配置里，用注释写清"本次唯一的变量是什么"和"为了它推迟了什么"。

### A8 ★ 越"看起来有希望"的早期读数越要警惕

A1 的四次都是同一个形状。项目已经形成了条件反射：
**看到 e0 大幅领先，第一反应应该是"这是不是瞬态"，而不是"这个改动有效"。**

---

### A9 ★★ 先做**零训练探针**，再花 GPU —— 本次直接省掉 2.2 小时

一个改动在动手实现**之前**，先问：它的**前提能不能用零训练的方式验证**。

v0.4.6 的做法是两项改动各自先做探针（§8.12.4）：
P1 逐尺度 token 表现（1 次前向）、P2 权重离线定标（纯离线）、
P3 统计量信息量（纯 CPU）、P4 污染量化（纯算术）。

* ★ **结果直接否掉了原方案**：提出的 $N_{\min}=8$ 经 P2 扫描后发现
  比现有静态权重**差 +0.0205，且四个长度桶全部更差** —— 按原方案跑就是白烧 2.2 小时 GPU。
  扫描还给出了修正值（$N_{\min}\ge 512$ 比静态好 −7.3%），最终按修正后的 64/0.5 实现。
* ★ **探针还给出了一条分析性结论**：原公式只有两个退化 regime
  （小锚点→均匀、大锚点→**与长度无关**），**无法表达“长度自适应”**
  —— 这是光靠跑实验很难看出来的。
* ⚠️ 但必须说清探针**测的是什么**：P2 是在**冻结模型**上做“事后重加权”，
  回答的是“怎样组合**现有** 5 个尺度的预测最优”，
  **不等于**“用哪套权重能**训出**最好的模型”。
  所以探针结论是**强提示，不是判决** —— 足以否掉一个明显更差的取值，不足以替代训练。

**规则**：新超参 / 新分支，先写探针把它的**前提**与**取值**定下来，把 GPU 只留给“训练本身”。

### A10 ★ 自检里的期望值必须来自“实际采用的参数”，不能从别处的表里抄

**自己踩的**：给 v0.4.6 写自检时，权重形状的期望值我抄了 §8.12.1 那张表 ——
而那张表是 **$N_{\min}=8,\ \tau=1$** 的，实际配置却是 **$N_{\min}=64,\ \tau=0.5$**。
于是 3 项**本来正确**的检查全报 FAIL。

危险之处在方向：**假失败会让人去“修”一段其实没错的代码**（甚至把正确的实现改坏）。

**规则**：期望值要么**从配置读**（`cfg["loss"]["token_weight_nmin"]`），要么显式写明来源；
自检失败时**先核对期望值本身**，再去动被测代码。

## B. 评测与产物（"静默出错"型，最危险）

### B1 ★★★ 评测必须用**训练时那一份 config**，否则结果静默变成垃圾

**事故**（2026-09-20）：用 v0.4.1 的 `configs/udet_v04_cons.yaml`（编码器 `codet5lora`，
逐 token）去评测 v0.4.2 的权重（`codet5blk`，分块）。编码器语义完全不同：

* m4 从 **0.9700 → 0.6731**、line 从 **0.7895 → 0.0127**
* 而 `state_dict` 的键基本对齐 ⇒ **不报任何错**

**已加防呆**：`run_eval` 比对 ckpt 同目录的 `config.yaml`，比对 `encoder` / `model` /
`heads` / `report` 四段（`loss`/`train` 不影响评测，不查；`block_batch`/`static`/
`compile`/`ckpt`/`chunk` 数学无关，跳过），不一致直接 `SystemExit(2)` 中止，
**且中止发生在写 `eval.json` 之前**。

### B2 ★★ 冒烟评测（`--limit`）绝不能覆盖正式产物

**事故**（2026-09-21）：为验证 B1 那个防呆而跑的一条 `--eval --limit 3`，
它**通过了防呆、真的做了一次评测**，把 v0.4.4 正式的 `eval.json` 与 `raw_*.pt`
全部覆盖成 3 样本版本（m4 显示 `1.0000`），而且不报错。

**已修**：带 `--limit` 时结果写入 `eval_limit<N>.json` 并打印警告。

★ 推广：**任何"测试/验证"动作都不应该写到正式产物路径上。**

### B3 ★★ 离线自检挡不住 dtype / 形状类的实现错误，必须有**端到端真跑**

`WindowedContextClassifier`（v0.4.x 的滑窗基线）连挂两次，都是离线 fp32 自检
**结构上不可能发现**的：

1. autocast 下 `h` 是 fp32、`token_head(h)` 是 bf16，用 `h.dtype` 当累加器会报
   `index_add_(): self (Float) and source (BFloat16) must have the same scalar type`；
2. token logits 形状必须是 `(B, 1, L)` —— 写成 `(B, L)` 会直接
   `ValueError: Target size ([1,1,3071]) must be the same as input size ([1,3071])`。

**规则**：自检至少要包含 ①**混合精度（autocast）**用例 ②**端到端跑通**一次
（哪怕 `--limit 8 --epochs 1`）。

### B4 ★★ checkpoint 必须存 `state_dict()`，不能只存 `named_parameters()`

漏掉 BatchNorm 的 `running_mean`/`running_var` 后，加载回来的模型会崩
（m4 F1 **0.86 → 0.66**）。

### B5 ★ 比较吞吐**不要用 `tok_s`**，要用 `metrics.csv` 的 `sec` 列

`tokens_seen` 在 `train.py` 里是**整个 run 只初始化一次**（在 epoch 循环之外），
而 `elapsed` 每轮重置 ⇒ `tok_s = tokens_seen / elapsed` 会被放大"已跑轮数"倍。
v0.4.1 读的是第 4 个 epoch、显示 25,763，真实值应约 12,600。

### B6 ★ 阈值不要写死 0.5

仓库内评测把判定阈值写死 0.5，但扫描后发现**各模型偏好差别很大**：
基线偏好 **0.55~0.70**、U-Det 偏好 **0.35~0.40**（U-Det 输出概率系统性偏低）。
各自取最优阈值后，line 的差距从 −1.00 收窄到 **−0.40**（六成差距来自工作点）。

**规则**：不平衡的分割任务按验证集选阈值；把 0.5 写死会让对比失真。

### B7 ★ `best.pt` 按 val 的 monitor 选 ⇒ 引用 test 差距时要说清这个偏差

v0.4.4 的 m4：val 0.9681 / test **0.9775**；基线的 m4：val 0.9812 / test **0.9736**。
两边选的未必是 test 上最好的那个 epoch。**引用差距以 test 为准，但要知道它带着选择偏差。**

### B8 ★ 评测是确定性的 —— 可以拿它做回归

同一 config + 同一 ckpt 复跑，指标逐位一致（实测多次）。
所以"重跑评测"是安全的恢复手段，也可以用来验证产物没被动过。

---

### B9 ★★ `eval.json` 落在 **ckpt 所在目录**，不是 `--tag` 目录

`run_eval` 的输出路径是 `Path(ckpt).parent / "eval{suffix}.json"`
—— **`--tag` 只影响训练产物，不影响评测产物**。

**差点造成事故**：为了做“向后兼容”的回归验证，需要拿旧配置重评 v0.4.5 的权重。
若直接 `--eval --ckpt runs/v0.4.5/best.pt`，就会**覆盖 v0.4.5 正式的 eval.json**。
正确做法是把 `best.pt` + `config.yaml` **复制到临时目录**，对副本评测，比完再删
（`config.yaml` 必须一起复制，否则配置防呆会因找不到它而**静默跳过**）。

**规则**：任何“重评已归档的 run”的动作，先确认输出路径会不会踩到正式产物。

## C. 数据特性（会静默把指标变成噪声）

### C1 ★★ hybrid 的样本标签恒为 1

`build_subset.py` 只保留含 AI 行的文件 ⇒ **hybrid 的样本级标签全是 1**。
所以：

* 样本级 CE **只能**在 m4 上回传（`train.sample_streams: [m4]`）；
* 如果把它算进样本级指标，它会**随模型变好而下降**（见 C3）。

### C2 ★★ m4 的长度与标签强混淆

**AI 样本全部 <2048 token，4096+ 全是 human。** 后果：

* 纯长度规则就能在 val 上拿到 **0.659** 准确率；
* **长度分桶时，m4 的 `>2048` 桶全是 human** ⇒ F1 退化成 0/0，
  那个桶的数字**不能用来判断任何事**（本项目一度据此以为"长文档全错"）。

### C3 ★★ monitor 必须排除退化的流

`_monitor_score` 原本把所有流的 `sample_f1` 都算进 mean，而 hybrid 的样本标签恒为 1
（C1），它的 `sample_f1` 会**随 token 级变好而下降** ——
v0.3 首跑时 epoch1 0.4833 → epoch2 0.3718，把四项全优的 epoch 2 压掉了。

**规则**：选 ckpt 的指标里，每个分量都要先确认"它变好 == 模型变好"。

## D. 工程与运维

### D1 ★★ 后台任务启动后**必须核对日志 + 进程**

**事故**：v0.4.4 第一次启动被**静默吞掉** —— 队列日志 0 字节、无进程、GPU 空闲。
原因是把 `setsid nohup ... &` 和前面的 `git add/commit/log` 串在同一条命令里。

**规则**：启动后必须查 `cat 队列日志` + `pgrep -af` + `nvidia-smi` 三件套，
不能因为"命令返回了"就认为起来了。

### D2 ★★ 杀任务的顺序：**看门狗 → 队列 → 训练**

如果先杀训练：队列脚本的 `wait $!` 立刻返回，于是它**拿半成品的 `best.pt` 去评测、
写出 `eval.json`** ⇒ 看门狗看到 `eval.json` 存在，以为任务完成、**之后再崩就没人兜底**。

### D3 ★ 主进程死后 dataloader 子进程会变成孤儿、继续占显存

主进程被 kill 后，8 个 dataloader worker 会被 init 收养并继续持有 CUDA 上下文
（实测显存 8590 MiB 不释放）。清理方式：

```bash
ps -eo pid,ppid,cmd --no-headers | awk '$2==1 && /train\.py/ {print $1}' | xargs -r kill
```

用 `$2==1` 限定孤儿可**避免匹配到自己这条命令**。

### D4 ★ 单实例保护：用 **PID 文件 + `kill -0`**，不要用 flock、也不要用 `pgrep -f`

两种"标准写法"本项目都实测失效过：

1. **`flock`**：fd 会被子进程（`sleep`）继承。看门狗被 kill 后，残留的 `sleep 300`
   **永久占住锁文件**，新看门狗一直报"已有看门狗在运行"。
   （排查方法：`readlink /proc/<pid>/fd/9`）
2. **`pgrep -f 'bash scripts/watchdog.sh'`**：会被**命令行里提到脚本名**的外层 shell
   误命中 —— 启动命令本身就是一串含该脚本名的文本。

### D5 ★ 后台训练的日志要**直接重定向**，不要过 `tee` / `grep` 管道

管道会缓冲，导致看不到实时进度。

### D6 ★ `tail -c N` 会截断数字，别用它读进度

tqdm 的 `[58:55<...]` 被 `tail -c` 从中间切开后变成 `08:55`，据此判断进度会得出错误结论。
**正确做法**：`tr '\r' '\n' < log | grep -E "^epoch" | tail -1`。

### D7 ★ 显存 / 性能类（v0.2–v0.4 累积）

| 现象 | 根因 | 正确做法 |
| --- | --- | --- |
| `CUFFT_INTERNAL_ERROR`，显存爬到 11.9GB | cuFFT plan 数随长度无界增长 | FFT 一律在 **≥ 真实长度的 2 的幂**上做（尾部补零），算完裁回 |
| 显存 9.47GB / 194ms | 先 `gather` 出 `(B,L_out,win,D)` 再投影 k/v | **先在紧凑序列上算 k/v 再 gather** ⇒ 5.90GB / 96ms |
| q/k 变成死参数 | `seq_len=1` ⇒ softmax 单元素恒为 1 | 分块（见 A5） |
| 逐 token 前向很慢 | 固定开销占 2/3 以上 | `torch.compile` + **静态形状**（`static` 把块数补齐） |
| 上采样路径吃掉一半算力与 5.8GB 显存 | gather 式窗口跨注意力 | 单任务消融时确认它是**净正收益**（§8.8），不要随手删 |
| LoRA `lr_encoder=3e-4` 一 epoch 就把编码器输出改变 139% | 适配器 LR 要按"它影响下游全部特征"来定 | 降到 `5e-5` |
| 容器里 `OMP_NUM_THREADS=0`（无效值），libgomp 报 `Invalid value...` | AutoDL 镜像的环境变量 | 每条命令前加 `OMP_NUM_THREADS=8`；读 ckpt 的小脚本用 `OMP_NUM_THREADS=1` |

### D8 ★★ 数"已完成几个 epoch"要读 `last.pt`，**不要**数 `metrics.csv`

`metrics.csv` 是每个 `log_every`（=200 步）写一行的，**进行中的 epoch 也会被写进去**。
实测：v0.4.5 刚跑到 `epoch 2` 的 20% 时，csv 里已经有 `0 / 1 / 2` 三个不同的 epoch 值
⇒ 若按"distinct epoch 数"判断，会以为已完成 **3** 轮（实际只有 2 轮），
看门狗于是**少补一轮**，要等下一次重试才自愈。

**正确做法**：读 `last.pt` 的 `epoch` 字段（= 最后一次**完整跑完**的 epoch 下标），
已完成轮数 = `epoch + 1`；只有 ckpt 读不出来时才退回数 csv 当兜底。

### D9 ★ 看门狗必须**参数化 + 判据可验证**，不能写死目标

第一版 `scripts/watchdog.sh` 把目标（`base_codet5_tok` + `v0.4.2`）写死在脚本里，
产出后正常退出。**换任务时它既不报错、也不会帮忙** —— 一旦没注意，就会以为"有看门狗兜底"
而实际整晚无人值守。后来的 `scripts/watchdog_run.sh` 改成参数化：

```bash
bash scripts/watchdog_run.sh <TAG> <CONFIG> <EPOCHS> [--dump-raw]
```

判据也从"`eval.json` 存在"升级为"**`eval.json` 比 `best.pt` 新**" ——
否则上一轮留下的旧 `eval.json` 会让它误判完成（与 B2 是同一类错误）。
启动后同样必须验三件套（D1），其中 **`PPID` 应为 1**（确认真的脱离了终端）。

### D10 ★★★ 容器内的看门狗**防不住实例级关机** —— 真正的连续性来自 ckpt + resume

**事故（2026-09-21）**：08:30 实例被关机，09:03:36 容器重启
（`PID 1` = `bash /init/boot/boot.sh`）。此时：

* 训练停在 `epoch 3` 的 45%，日志**戛然而止**；
* **队列脚本、接力脚本、看门狗三个兄弟进程一起消失**，都没留下任何退出信息；
* GPU 空闲、无孤儿进程、`memory.events` 的 `oom_kill 0`（**不是 OOM**）。

**结论**：`watchdog + queue + train` 是同一容器里的兄弟进程，**实例一关就全死**。
在容器内做多少层看门狗，都防不住“实例被关机 / 被停止”。
（`setsid nohup` 只能防住“终端关闭”，防不住容器级终止。）

**真正救回数据的是**：
1. **`last.pt` 每轮落盘 + `metrics.csv` 追加** ⇒ 重启后可以 `--resume` 精确接着跑；
2. 接力脚本里**提前存的 2 轮快照**（`eval_2ep.json` / `raw_*_2ep.pt` / `best_2ep.pt`）
   ⇒ 目标轮数后来被改成 4 轮，而 2 轮的同预算数据仍然拿得到。

**规则**：把“任务连续性”寄托在**落盘的检查点**上，而不是寄托在常驻进程上。
跨夜任务启动时就要想清楚：**如果中途断电，我能恢复到哪一步？**

### D11 ★ 判断“容器是否重启”要用 `ps -o lstart -p 1`，**不要用 `uptime`**

这次排查差点被 `uptime` 带偏：它报 `up 3 days 22:21`，看起来容器根本没重启。
实际上 `/proc/uptime` 与 `uptime` 在这个容器里报的是**宿主**的 uptime
（339714s ≈ 3.93 天），**容器重启不会把它清零**。

**正确判据**：`ps -o pid,lstart,etime,cmd -p 1` ——
PID 1 的启动时刻就是容器的启动时刻（本次显示 `Mon Sep 21 09:03:36 2026`）。
旁证：`/tmp/supervisord.pid` 的 mtime 会跟着更新。

### D12 ★ dataloader worker 会把 `tok_labels` 的**维度约定**带进探针脚本

自己写探针时把 `tok_labels` 当成 1-D 用，`avg_pool1d` 立刻报
`Given input size: (3200x1x1) ... Output size is too small`。
原因：`token_loss` 里的 `tok_labels` 是 **`(1, L)`**，
而 1-D 的 `v.unsqueeze(1)` 得到 `(L, 1)`，`avg_pool1d` 会把 **batch 维当成长度**。

**规则**：从 dataset item 取标量/序列时，**先对齐模型内部的维度约定**（这里必须 `unsqueeze(0)`）。
